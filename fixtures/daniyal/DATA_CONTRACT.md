# Данные и договор форматов

Версия 1. Это предложение для согласования с Ильясом, а не описание существующего API. Язык backend, функции и endpoints не определены.

## Источники и смысл
Данные перенесены из двух предоставленных DOCX: «Датасет районов» и полного кейса «Аким на 5 часов». Это синтетическая учебная модель. Географические координаты, реальная статистика, прогнозы и дополнительные мероприятия не добавлялись.

Числа и правила совпали с документами. Общее описание говорит о пяти направлениях; подробный датасет уточняет: ровно пять мероприятий, максимум два одного направления, то есть минимум три направления. Требования «ровно одно каждого направления» нет.
В документе Score базы округлён до 52.56, пример дан приблизительно 56.5; точные значения при расчёте без промежуточного округления — 52.55768 и 56.54307.

## city-data.json
- schemaVersion: версия структуры; synthetic: данные синтетические; sources: имена источников.
- budget: 100; budgetUnit: условные единицы, не тенге; horizonQuarters: 8 кварталов.
- scale: допустимые границы показателей и направление «больше — лучше».
- directions: id и русское name.
- indicators: id, name, directionId, weight, scaleMeaning. Неуказанное в источнике описание нуля не придумывается.
- districts: id, name, populationShare (доля, не проценты), indicators (исходные значения), referenceScore (опубликованная оценка для сверки), description.
- measures: id, name, directionId, scope (city или district), cost, lagQuarters, effects (полные прибавки до учёта лага; отрицательные допустимы).
- synergies: id, measureIds (обе меры обязательны), targetMeasureId (район этой меры получает бонус), effects (фиксированный бонус без лага).
- incompatibilities: measureIds, scope (scenario — любой район; sameDistrict — только один район), reason.
- rules: ровно 5, одна мера максимум один раз, максимум 2 меры направления, требования к району, независимость от порядка, отсутствие бонуса за остаток, null вместо Score при ошибке.
- scoreFormula: веса среднего и минимума, штраф, порог и строгое сравнение, порядок ограничения показателей, отсутствие лага у синергий, число знаков отображения.

## Предлагаемый вход
Районная мера: `{"measureId":"M7","districtId":"nura"}`.
Городская: `{"measureId":"M12","districtId":null}`.
Сценарий: объект `{"decisions":[...]}`.
Для городской меры null означает отсутствие района; пропущенное поле также принимается проверочным скриптом. Для районной отсутствие поля или null — ошибка. Пустая строка не считается корректным районом.
Повторы определяются по measureId, даже если районы разные.

## Порядок вычислений
1. Проверить все ограничения. При нарушениях вернуть valid=false, список violations и score=null. Не вычислять итоговую оценку.
2. Взять исходные показатели. Прибавить эффекты каждой меры, умноженные на (8 − lagQuarters)/8. Городская мера применяется ко всем пяти районам.
3. Прибавить активные фиксированные синергии в районе targetMeasureId.
4. Один раз ограничить каждый итоговый показатель диапазоном 0–100, после суммирования всех эффектов.
5. Для района вычислить сумму indicator × weight.
6. Среднее города — сумма districtScore × populationShare. Найти минимальную оценку района.
7. Посчитать все пары «район × показатель» со значением строго меньше 40.
8. Score = 0.7 × averageScore + 0.3 × minimumScore − criticalCount.
9. delta = Score − базовый Score. Остаток бюджета не влияет на Score.

База без действий нужна для сравнения, но пустой пользовательский сценарий невалиден. Итоговый Score отдельно не ограничивается 0–100: такого требования в формуле нет.

## Предлагаемый результат и эталоны
В scenario-fixtures.json поле expected задаёт:
- valid и violations: валидность и предлагаемые уникальные коды нарушений;
- cost, budgetRemaining: сумма и остаток;
- finalIndicators: словарь районов с десятью итоговыми показателями;
- districtScores: оценки районов;
- averageScore, minimumScore, worstDistrictIds: среднее, минимум и все районы, делящие минимум;
- criticalIndicators: список districtId, indicatorId, value; criticalCount: его длина;
- score, delta: итог и изменение относительно базы;
- appliedSynergies: идентификаторы применённых бонусов.

При ошибке эталон содержит только valid=false, violations и score=null. Не нужно требовать совпадения текста ошибки. Коды — предложение команды, Ильяс может сопоставить их со своими. Для неизвестной меры её стоимость и направление не угадываются; остальные известные решения всё равно проверяются.

Коды: DECISION_COUNT, DUPLICATE_MEASURE, BUDGET_EXCEEDED, DIRECTION_LIMIT, DISTRICT_REQUIRED, CITY_DISTRICT_FORBIDDEN, UNKNOWN_DISTRICT, UNKNOWN_MEASURE, INCOMPATIBLE_SCENARIO, INCOMPATIBLE_DISTRICT.

Каждый из 15 ошибочных сценариев изолирует одну категорию ошибки. Это тесты бизнес-правил для объектов указанной формы, не полный набор тестов безопасности/типов входа API. Обработку произвольного некорректного JSON согласовать с Ильясом.

## Точность и сверка
JSON содержит числа, а не строки. Эталонные десятичные результаты сохранены без потери значащих знаков для данного датасета. Проверочный скрипт читает дроби через Decimal и сравнивает точно. На backend с обычными числами использовать абсолютную погрешность 1e-8.
Округлять только отображение, до 2 знаков. Пример: 56.54307 − 52.55768 = 3.98539 → +3.99. Вычитание отображаемых 56.54 и 52.56 ошибочно даст 3.98.
Порядок элементов в violations, appliedSynergies и criticalIndicators не имеет смыслового значения. В файле порядок фиксирован ради воспроизводимости; при адаптации к backend сравнивать их по содержимому.
